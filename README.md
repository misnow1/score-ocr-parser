# score-ocr-parser

Extract the instrumentation and solos and features, and draft a planner flow, from big-band conductor score PDFs. Runs locally; the PDFs are read in place and never copied.

## Setup

Requires Python 3.12 and [uv](https://docs.astral.sh/uv/).

```
uv sync
uv run pytest
```

OCR tests are macOS-only and are skipped elsewhere; CI runs them on a macOS runner.

## Usage

```
uv run score-parser parse SCORE.pdf [FOLDER ...] --out out [--format json|yaml|both] [--numbers-dir DIR] [--parts-dir DIR] [--force-ocr]
uv run score-parser inspect SCORE.pdf --page 1 [--tokens | --layout] [--force-ocr]
```

- `parse` writes, per PDF, the JSON report `<score>.json` and/or the flow draft `<name>.yaml` into the output directory (default `out/`, git-ignored), chosen by `--format` (`json` default, `yaml`, or `both`), and prints a summary table (see Folder runs).
- `inspect` prints one page's cleaned tokens (default) or the label stacks and lines to stdout. It never writes files.

Library use:

```python
from score_parser import parse_score
report = parse_score("SCORE.pdf")
report.instrumentation, report.unknown_labels
```

The JSON report (`report.to_dict()`) has these fields:

- `title`, `title_source`, `matched_slug`, `draft_name`, `unmatched`;
- `instrumentation[]`: `instrument`, `family`, `chairs`, `labels`, `doublings`;
- `features[]`: `kind` (`solo`, `feature` or `vocal lead`), `instrument`, `chair`, `chair_ambiguous`, `voice` and `section` (vocal leads), `shared_with[]` (the other instruments of a shared marking, each `{instrument, chair, chair_ambiguous}`; empty for a single-instrument feature), `page`, `bar`, `rehearsal_mark`, `mark_carried_from` (the page a carried mark is printed on; null when it is on the feature's own page), `raw_text`, `confidence`, `reasons`, and `locations[]` (each `{page, bar}`: the first appearance of a merged feature, then its reminders);
- `flow[]`: the draft steps in score order (`section`, `instrument`, `note`, `todo`, and `mark`, the rehearsal mark the step is grouped under, null for no section);
- `unknown_labels`, `warnings`;
- `pages[]`: `page`, `source` (`text` or `ocr`), `ocr_confidence`, `dpi`, `reason` (`text`, `image`, `pattern` or `empty`: why the page was read that way) and `rotation` (degrees clockwise the scan is printed rotated: 0, 90 or 270; 0 for text pages).

Each page is classified with a reason, recorded as `report.pages[].reason`: `text` (has a text layer), `image` (almost no text words plus a page-sized image), `pattern` (almost no text words and the page draws its content as a tiling-pattern fill, which hides the image from image detection) or `empty` (no text words and nothing else). A page with a few words but no scan image or pattern keeps its text layer (`text`). Every page but `text` is sent to OCR automatically; `pattern` and `empty` pages are rendered whole at 300 dpi first. A page that yields no tokens, and a score whose instrumentation comes back empty, add entries to `report.warnings`, so zero results are never silent. Scans are read with Apple Vision OCR (macOS only, via pyobjc; installed on macOS only). OCR yields the same positioned words as a text layer. The embedded image is read at native resolution; pages under about 300 dpi are upscaled to 300 dpi. Recognition is accurate-level with language correction off and the alias table as custom vocabulary. `--force-ocr` (CLI) or `ParseOptions(force_ocr=True)` OCRs every page regardless of text layer. `report.pages` records each page's `source` (`text` or `ocr`), `ocr_confidence` and `dpi`; pages under 150 dpi or below 0.5 mean OCR confidence add entries to `report.warnings` (the CLI prints them). Scans printed sideways are handled by trying three orientations per page (content rotated 0, 90 or 270 degrees clockwise): the image is turned upright for each, OCR runs, and the best wins by instrument-word hits in the left half of the upright page (staff labels sit left of the staves, and Vision also reads upside-down text, so it can't pick by confidence alone), then total hits, then mean confidence. Tokens come back in the upright frame and `Page` width and height are swapped for a turned scan, so layout sees an upright page. The chosen rotation is recorded as `report.pages[].rotation` (0 for text pages). The text-layer path imports nothing macOS-specific, so it stays cross-platform. Where Apple Vision is unavailable, a page that needs OCR keeps whatever text layer it has and adds a warning ("no text found ... OCR unavailable") instead of failing.

Current scope: text-layer PDFs and scans. The report lists the instruments on the first system (full names), with:

- chairs, expanded from ranges ("1-4", "1–4", "Tbn.1-4", "i & II"). OCR label repair: a capital I (or "l", "|") or a digit glued to a name ("TRUMPETI", "TENOR SAXI", "TRUMPET1", "Gtr.l") is that chair, 1 for the letters (only when the whole label is no known alias, so "Pianol" and "Drums1" are chair 1 and a real word is never cut); a number above 9 beside a label ("TROMBONE 29") is a bar number, not a chair, and is dropped;
- combined labels: "Trb. 3, Tba." gives Trombone chair 3 and Tuba chair 1. Each part must resolve, or the whole label is unrecognised; each part is then cross-checked like a single label (see the later-system rule below);
- part-filename spellings, so a part's instrument can be read from its file name (#57): words run together or abbreviated ("BariSax", "AltoSaxes1-2", "TenSax 1", "AcoustGuitar", "ElecGuitar", "Flts1,2"), a chair running on after a letter when it is a digit ("Flts1,2", "AltoSax1/2"; a "/" also separates chairs), and a slash between two instruments ("Keyboard/Synth" is Keyboard chair 1 and Synthesizer chair 1, like a comma). A label that names several instruments written run together ("KeyboardSynth", "KeyboardOrgan") is listed under `combined_aliases` in `data/aliases.yaml` and splits into its parts. "Keyboard" and "KEYS" are the canonical instrument Keyboard; it is not merged with Piano or Organ (the planner counts all three as keys, an open decision). "RHYTHMN" and "Rhythm" are the canonical instrument Rhythm, a rhythm part with a `warnings` line asking for review: the part could be percussion and toys or the drum kit, so no instrument is guessed (a printed "Rhythm" staff label is still a group label and ignored, see `label_filters.yaml`). Choir and voice labels stay unrecognised. A name with no instrument ("Score", "lyrics only") is not mapped;
- doublings, from labels ("Flute (Oboe) 1-3") and from instruction text ("to Flute", "piccolo trpt"; a "Mute" marking is ignored). An instruction is attached to the staff label nearest to it vertically;
- non-standard instruments (violin, viola, cello, organ, guitars, french horn, tuba, percussion, synthesizer, sleigh bells, wood block ("W BL", "W. Bl."), cowbell ("C BL", "C. Bl."), lead vocal, flugelhorn, piccolo trumpet, and others in the alias table).

Staff labels are found as a column at the left of the staves. Notation programs right-align them (short names such as "Piano" or "Picc." start further right), so the column is found from labels sharing a right edge, or a left edge for left-aligned scores, whichever lines up more labels. Each line is cut to its label at the first gap of 8 pt or more, glyph residue, chord symbol ("Pno. D D A7") or time signature ("Baritone Saxophone 44": the 44 is never read as a chair). Running titles (a long line repeating on several pages), score and group tags ("Score 5", "Trumpets"), credit and footer lines, lone chords and dynamics, and one- or two-letter glyph residue are not labels (`data/label_filters.yaml`). Label column repair: words printed over each other (an overprinted "Piccolo" and "Alto Sax I & II") are read as two lines, upper first. A repeated line is a running title only if it has real words (a repeated "A. Sx. I & II" is a label). A bare "B" between a chair and a word is a transposition ("1&2 B Tpt." is Trumpet 1-2), and a leading chair ("1&2 ...") is read like a trailing one. Group tags such as "TBNS", wholly parenthesised lines ("(Memory out front)"), lines ending in dots ("Drums only......") and tempo or feel text ("Swing Feel in 8ths") are not labels. Staff count: the clef glyphs that the clean stage removes are kept on `Page.glyphs`; clefs sharing the leftmost shared x right of the labels are the page's staves. A staff more than 0.6 label steps from every label adds one warning ("Page 1: 1 staff with no label ...", with how many more pages repeat it); it is judged only when the page has at least as many clefs as labels, so scans (no glyphs) and pages whose non-label lines were filtered are not flagged. A lone label more than 1.5 label steps from every neighbour and every clef (the text "Piano" printed by the title) is not a staff label. The first system is the stack with the most resolving labels on the first page that has any, not simply the topmost stack.

Abbreviated labels on later systems ("A. Sx. 1", "Tbn. 1-4", "E.B.", "D. S.") are cross-checked against the first system. The first system is only a heuristic pick, so an instrument it lacks is still a normal instrument of the score when its labels recur: one that appears on two or more later systems joins the instrumentation without a warning. Canonical-name variants count as one instrument (Bass and Electric Bass, listed in `data/instrument_variants.yaml`, applied by `present_as`); a variant label is filed under the entry already present. A label for an instrument that appears on only one later system, an abbreviated label ("Tbn. 5") with a chair outside the first system's chairs for an instrument it has, or a label that cannot be resolved adds a message to `warnings`. A label that cannot be resolved warns once per score, however many pages it appears on, with its page count, the first system's page included ("label 'Kazoo' is not recognised (on 12 pages)"); a label unresolved only on the first system is listed in `unknown_labels` without a warning. A later label that repeats the full name ("TRUMPET 4", since the score does not abbreviate on later pages) with a chair the first system lacks joins that instrument without a warning. Unresolved labels also go to `unknown_labels`, never guessed. Voice staves are not instruments and not unknown labels: a choir label ("SATB", "TB", "Choir"; never "AB", an OCR read of "A.B.", Acoustic Bass), a "Voice Lead F" or "Voice bck" staff, a run of two or more part abbreviations ("A.", "Bar."), and the staves under a "VOCALS" group label (a label printed between two staves, closer to both than staves are to each other, so "Alto" under it is not Alto Sax). They stay out of the instrument table, and a solo over one never takes an instrument from it. A lone "A." or "Bar." (which can be a vocal part) and "VCLS" are still unresolved labels. "Cello-Bass" is one staff for Cello and Double Bass and is reported as its own combined entry with a `warnings` line asking for review: the score cannot say which instrument plays it, so it is never mapped to Bass or Electric Bass (`review` in `data/aliases.yaml`). "A.B." is Acoustic Bass (Bass); "Vibes", "Vib." and "Vibraphone" are Vibraphone. A combined label ("Trb. 3, Tba.") counts as each of its instruments: every part is checked on its own, so a part that recurs is accepted while another part with a chair outside the first system's still warns.
Music-font glyphs are removed before reading. A word's font comes from its own characters (empty when they span several fonts). A token is dropped when it is set in a font listed in `music_fonts.yaml` (Sibelius Opus and Finale Jazz, Maestro and BroadwayCopyist glyphs look like plain characters, so only the font name identifies them; fonts whose name contains `text` are kept), or when it is a text-layer token with an empty font that holds only glyph characters (`music_glyphs` in the same file) or any non-ASCII one, or private-use characters. OCR tokens have no font and are never dropped as music ("&" in "Alto Sax 1 & 2" stays). The alias table (`aliases.yaml`) and `music_fonts.yaml` are editable data in `src/score_parser/data/`.

Solo and feature detection: `report.features` lists every solo or feature marking ("ALTO SOLO", "1x - Solo", "Male vocal solo", "vamp for drum feature") with kind, instrument (from the text, else from the staff it sits on; a staff never gives an instrument the first-system instrumentation lacks; an instrument named in the text but missing from it is kept as a possible feature, see below), page, nearest bar number, current rehearsal mark, raw text, confidence and reasons. Layout analysis finds systems (stacks of staff labels from the label column), staff bands, bar numbers and rehearsal marks (single capitals and section words listed in `data/rehearsal_words.yaml`), and splits glued tokens such as "29ALTO SOLO". Vocal leads are a separate feature kind, `vocal lead` (see below), and are never instruments. A mark printed beside a digit or text in one row ("C VERSE 2") is split off it. The current mark runs from one mark to the next in reading order and carries across page turns until the next mark (ADR 0003): a feature on a page that prints no mark gets the last mark printed on an earlier page, with `mark_carried_from` set to that page, a reason "mark carried from p15" and confidence 0.05 lower. A feature before the first mark of the score has no mark. `report.features` is in score order: by page, then bar, then x position of the first location (a feature with no bar follows the barred ones on its page, ordered by system, then x; a later reminder never moves a feature, the first copy places it). A vocal feature with solo wording needs the word male, female, vocal or vox directly before the solo wording; "male" or "female" alone scores lower than "vocal" or "vox". Bar numbers are printed sparsely, so on text-layer pages a feature's bar is counted: the drawn barlines (vertical rules from the PDF's vector drawings, at least 20 pt tall) between the nearest printed number and the text are added to that number, so a solo mid-system gets its own bar, not the system's first (ADR 0002). A number centred inside its bar (clear of both barlines) numbers the bar that starts at the barline to its left; one centred on or just right of a barline numbers the bar that starts there. Stacks of one system share one row of bars; a row with no printed number continues from the bars of the row before, and the first row of the score starts at bar 1. A reminder on a later row only joins a feature when it sits in that row's first bar. (A vocal lead over a page turn is the exception, see the vocal leads paragraph.) OCR pages have no drawn rules: they keep the nearest printed number, with lower confidence and a reason saying the bar may be earlier than the true one; a text-layer page with no drawn barlines does the same without the penalty. Text left of every bar number on a system with no barlines takes the first bar with lower confidence and a reason saying so. Copies are merged: a solo printed above every staff, and reminders on later systems and pages, become one feature (same kind and instrument on the same or the next system; a system without it in between starts a new one). A copy is a reminder only when it also fits the solo it would join: on a later system it keeps the chair (a bare "SOLO" above "Gtr. 2" after one above "Gtr. 1" is another solo), it is no more than 16 bars on, and on another row of bars it sits in that row's first bar; otherwise it is a separate feature of the same instrument. `locations` lists each distinct page and bar; `page`, `bar` and `rehearsal_mark` are those of the first appearance; confidence, reasons and raw text come from the best-evidenced copy. Vocal leads naming different sections ("Verse 1", "Verse 2") never merge. Chair: `chair` is set from the marking text ("GUITAR 1 SOLO", "TRUMPET 3"), else from the staff: a bare "SOLO" above a numbered staff ("Gtr. 2"), or an unnumbered "GUITAR SOLO" printed above that instrument's own numbered staff (copies above every staff do not count). The text wins over the staff. Shared features: one bare marking printed at the same place (same wording, same system, same bar, within 3 pt across) over the staves of several different instruments is one feature, not one per staff: `instrument` and `chair` name the topmost instrument and `shared_with` the others, in staff order, each with its chair; `locations` cover them all. Wording that differs, or the same wording printed apart, stays separate features. Copies of one marking across the staves of one system fold into one feature whether or not they name an instrument: a copy with no instrument (over a staff whose label resolves to none) joins the copy of the same wording that has one. A generic wording (no instrument in its text) printed at one place (x within 3 pt) over more than half of the staves, at least four of them ("Open Solo", "(SOLOS)"), is an open solo: the feature has no instrument (it is not given to the staff it happens to sit above), and the flow draft gets a TODO. A bare "SOLO" that coincides over a few staves stays one shared feature; it is an open solo only over all but at most one staff. Another bare solo on that system folds into an open one only when it is within 16 bars of it, or, when a bar is unknown (a scan, a page with no bar numbers), at the same place. A text-named instrument is never made open, and that includes a named instrument the score lacks (a possible feature: "VIOLIN SOLO" over every staff). Solos at different places on one system stay separate features. A voice part in the text ("Tenor Solo", "Bass Solo") over a choir staff is a vocal lead, not the sax or the bass; "Tenor Sax Solo" there keeps its instrument, and a "feature" wording over a choir staff is a feature, not a vocal lead. Copies naming different chairs stay separate features ("GUITAR 1 SOLO" and "GUITAR 2 SOLO"). A staff shared by several chairs ("Gtrs.", "Guitars", "Gtr. 1 & 2") is never guessed: `chair` stays empty and `chair_ambiguous` is true. Chord symbols ("F6", "G7", "Bbmaj7(b5)/G") are stripped from `raw_text`, including several run together ("Bbmaj7(b5)/GA9") and one glued to the wording ("E9Solo"). Chord text alone never makes a feature. Chord text over a bare "Solo" (no instrument in the wording) is a chart label when it holds two or more chords (dropped, with a warning so it can be reviewed); a single chord before a bare "Solo" ("G7 SOLO") is kept as a possible feature: confidence below the flow TODO threshold, a reason saying the wording was only chord text plus "Solo", and a TODO in the flow draft. A solo text that names an instrument missing from the instrumentation (its part is a separate file: "violin solo" over a piano-only score) is kept as a possible feature: `instrument` is the named one, confidence is lower (below the flow's TODO threshold), a reason says it is not in this score's instrumentation, the flow draft gets a TODO, and a warning is added. The staff it sits above is never taken as the soloist's; only text-named instruments are kept this way. Text containing "solo" or "feature" is never taken as a staff label, a number equal to the page number in the label column or right margin is not a bar number. A number is accepted as a bar number only when it sits in the bar row (6 to 60 pt above the top staff's label line, or, for a line of bare numbers, 4 to 25 pt under the bottom staff's label line, where some scores print one number per bar, two or more rising left to right (a lone digit or repeated 3s are no bar numbers); such a line belongs to the system above it, not the one beneath), which rules out time signatures on the staff, running headers ("10 Score") and triplet numbers inside the system; bar numbers must also rise through the score, so a number that breaks the longest non-decreasing run in reading order (a triplet 3 among bars in the 40s) is dropped. A feature with no accepted bar nearby keeps `bar: null`; it is never dropped.

Vocal leads: a feature with `kind: "vocal lead"`, no `instrument`, a `voice` (`female` or `male`), a `section` ("Verse 1") when the marking gives one, and the usual page, bar, rehearsal mark and locations. Two markings make one: a text such as "Female Lead Verse 1" or "Male Lead", and a bare "solo" above a "Voice Lead F" or "Voice Lead M" staff (the trailing F or M stays part of the staff label). A text and a solo on the same system are one feature. A bare "solo", "Verse 1x - Solo" or "Solo or All" above any other voice staff (a choir staff such as "SATB" or "TB", a vocal part abbreviation, a staff under a "VOCALS" group label) is also a vocal lead, with no `voice` (neither female nor male); a text printed just under a choir label, between its two staves, belongs to the choir and not to the instrument staff further down (a "(Solo)" over the TB line is no Piano solo). A cue that runs across a repeat or page turn is one feature: vocal cues merge with the next system that has voice staves, so a rhythm-section stack between two choir systems does not split them (the usual bar, row and section limits still apply). A bare "solo" above a "Voice bck" (backing vocal) staff is dropped. A voice named in the text scores higher than one read from the staff. Voice labels stay out of the instrument table, and instrument solos are unaffected.

A voiced lead (female or male) restated on the next system is one feature, and so over a page turn: the same voice on the next page's voice system, anywhere in the row and within 16 bars, joins it (`locations` lists both pages). It does not join when another voice's lead came between (the voice returning is a new lead, on any path: the same row, the next row or the next page), when a new rehearsal mark is in force, or when it names a section ("Verse 2") the lead before it lacks. A voiceless cue (a choir) keeps the first-bar rule and never turns the page. Systems with no voice staves in between do not separate two leads.
Vocal lead handover (no wording): where a score has both a "Voice Lead F" and a "Voice Lead M" staff, a change of lead is read from the staves themselves (ADR 0005). A lead staff sings in a bar when at least 5 lyric words sit under it (the band just under the staff, by the drawn barlines of a text-layer page); a bar where one lead staff sings and the other has fewer than 2 words belongs to that voice. When the voice that sings alone differs from the lead before it, a `vocal lead` feature is reported for the new voice at that bar, with the voice taken from the staff label alone, confidence 0.1 under a bare solo over a Voice Lead staff (0.7 with a counted bar, so the flow draft gets a TODO), and a reason naming the staff. A voice must sing alone twice within 3 bars, the other lead quiet in between, so a one-bar fill is no handover. The lead before is the voice of the latest of either, in reading order (system, then x): a lead marked in text, or a bar sung alone; the first voice to sing alone only starts the count and gets no feature. A handover whose text is printed ("Male Lead Verse 2") is one feature, not two. Bars where every voice sings, or both leads sing together, give no lead. The first bar of a system is read even when its left edge is not drawn as a barline (its bar number is then approximate). Scans (no drawn barlines) and scores whose voice staves carry no lyric words give none either, and a system that hides the empty staves of one lead voice has no pair to read (ADR 0005).

Flow draft (`--format yaml`, or `report.flow`): a `flow:` block in the shape mic-assignment-planner uses in `numbers/*.yaml`. One step per feature, in score order, each with `section` ("Alto Sax solo (B)"), `instrument` (lower case) and a `note` giving page, bar, rehearsal mark, chair ("chair 2", or "chair ambiguous (shared staff)") and confidence (a carried mark reads "rehearsal C (carried from page 15)"). Each run of steps under one rehearsal mark starts with a comment header (`# Section C`; a step with no mark falls under `# (no section)` and gets a TODO, `no rehearsal mark found: section unknown`, in both the draft and `report.flow`), so the steps of one section read together; the steps themselves keep the planner's shape. Steps below 0.8 confidence, with no instrument, or with an ambiguous chair, are followed by a `# TODO(score-parser)` comment giving the reasons. A shared feature is one step naming every instrument and chair (`section` "Soprano Sax, Clarinet and Trumpet 3 solo (A)", `instrument` "soprano sax, clarinet, trumpet 3"). A vocal lead is a step like "Female vocal lead, Verse 1 (B)" with instrument `vocal`. The draft never contains `kind` (vocal or instrumental) or `position` (DS1-DS5); those stay with the planner.

Title: the filename with noise removed ("SCORE", dates, years, "AJC", "(1)" and similar; words that can be part of a title, such as "copy", "final", "full" and "draft", go only in brackets, beside a dash, at the end of the name or next to such noise, so "The Final Countdown" and "Full Moon" are kept) and a trailing part name after a dash ("ERGUE A CASA - Piano" gives "ERGUE A CASA"; only a dash-separated instrument name is dropped, so "Piano Man" is kept); if nothing is left, the largest text on page 1. `report.title_source` says which (`filename` or `page 1`).

`--numbers-dir DIR` (or `ParseOptions(numbers_dir=...)`) points at the planner's `numbers/` folder, which is only read. The title is fuzzy-matched (rapidfuzz) against the slugs, each file's `title:` and the known aliases in `data/title_aliases.yaml` (First Noel = First Nowell, Superstition = Super Christmas = Merry Super Christmas, a parody of the same song, so "MERRY SUPER CHRISTMAS - lyrics only" matches the Superstition slug). A match needs a similarity of 85 and lengths within 60% of each other, so a short title such as "Sing" never matches "Sing Sing Sing". A match names the draft `<slug>.yaml` (`report.matched_slug`). With no match the draft is named `UNMATCHED-<title-slug>.yaml` and starts with an `UNMATCHED` comment. Without `--numbers-dir` the draft is named for the title slug. `parse` refuses an output directory inside the numbers directory, so it never writes into the planner repo.

Folder runs: `parse` accepts folders (every `*.pdf` in them, any letter case) and files together. After the run it prints a summary table with one row per score: instrument count, feature count and warning count, so charts that need a manual look stand out. If two scores would write the same output file name (for example the same matched slug), the later one gets `-2`, `-3` and so on, and a warning says so. Warning text goes to stderr. A score that fails to parse does not stop the run: its row shows `FAILED`, the error goes to stderr, and the exit code is 1 (0 when every score parsed).

Part files (library only, one file at a time; decisions in ADR 0004, ticket #58): `parse_part(path, show_context=None, options=None)` reads a one-instrument part with no label column and returns a `PartReport` (`parse_score` on a part behaves as before, finding no instrumentation). Parts are read in place, like scores.

```python
from score_parser import parse_part
report = parse_part("parts/alto-sax-1/Synthetic Tune Clarinet.pdf")
report.part.instrument, report.part.chairs, report.part.relation, report.features
```

- `title` (the filename without its part word and noise), `part`, `features[]` (the same fields as a score's: `page`, `bar`, `rehearsal_mark`, `confidence`, `reasons`, `chair`, `chair_ambiguous`), `bars[]` (the bars the part plays and rests, see inferring unmarked solos below), `pages[]` and `warnings`. There are no `instrumentation`, `unknown_labels` or `flow`: title words, verse words and music-font junk such as "&bb" never become labels or features.
- `part.instrument` and `part.chairs` come from the filename's part word at its end, resolved through the alias table. Noise words (copy, score, part, final, draft, AJC, years), "(copy)", "(1)", dashes and a ".pdf" remnant are skipped first; the part word is the longest run of up to six words (chair tokens count, "Tenor sax 1 & 2") that resolves and ends at the last or second-to-last word and does not start inside a bracketed group ("Short Tune (Reprise) Trpt1" keeps "(Reprise)" in the title), so "Sleigh Bells" is not "Bells" and "Bass Gtr" is Electric Bass, not Guitar. A digit glued to a name is a chair ("Trpt1" is Trumpet chair 1, "Tenor sax1-2" is chairs 1 and 2, "Trumpet 4-6" is 4, 5, 6, "Trombone II" is 2); no chair in the name gives `chairs: []`. `part.instrument_from` is `filename`. The filename wins whenever it names an instrument. A combined name ("KeyboardSynth") gives the first instrument in `part.instrument` and the others in `part.also`. When the filename names nothing the instrument folder gives the instrument (`instrument_from: folder`, "trumpet-3" is Trumpet chair 3). With neither, `instrument` is null, no solos are read and a warning says so.
- `part.player_slot` is the instrument folder the part sits in (who plays it); `part.slot_instrument` is what that folder resolves to and `part.slot_chairs` the chairs it names ("trumpet-3": [3]; empty when it names none). `part.relation` says how the filename's instrument relates to the slot: `same` (the same instrument or a variant: Bass and Electric Bass), `doubling` (one family or a listed pair in `data/part_doublings.yaml`: the Clarinet part in `alto-sax-1/` is "player slot alto-sax-1 (Alto Sax) plays Clarinet" in `part.note`, no warning; a Piano part in `keys/`; a Tuba part in `trombone-3/`), `unexplained` (a cross-family disagreement in no list, such as a Trombone part in a sax folder: the note is added to `warnings` and nothing is corrected, since only show knowledge can tell a misfiled part), or `unknown` (the folder names no instrument). A right instrument in the wrong chair's folder stays `same` with a note ("player slot trumpet-3 is chair 3; the part is chair 1"). `show_context` is where the planner's person-to-part metadata will plug in (a future release); it is accepted and not read yet, and the doubling report is what it will confirm or override.
- Solos: a part has one instrument, so a solo or feature marking in it is that instrument's. Staves are found from the long horizontal rules drawn as staff lines (runs of at least three, text-layer parts only; a percussion part, one of `one_line_staves` in `data/part_doublings.yaml`, may also draw one-line staves, accepted when at least two barlines run through the rule; a part with no staves warns "no staves found"), barlines from the short vertical rules running from a staff's top line to its bottom line, the staff's left end counting as the first barline. Text above the first staff by more than 60 pt (title, instrument heading) is page furniture. A part prints a bar number at the start of each staff, so only a number near a staff's left end is a bar number; the bar of a solo is counted from it by barlines as in score mode (ADR 0002). A staff-sized digit sitting on a staff (a music-font digit or one at least 1.5 staff heights tall), or one at least 0.95 staff heights tall that ends within 6 pt above the staff's top line or crosses it by up to 2 pt (where most parts print it), is a multi-bar rest: its interval counts that many bars, and the bar's reason says so. A digit on the staff within 80 pt of the staff's left end is the time signature, not a rest (a time signature never sits above the staff); a digit above the staff within 30 pt of its left end is a bar number. Some parts print a staff's first bar both above the staff and under it, and then the number under one staff and the number above the next can sit on top of each other (33 under one staff and 56 above the next, in one spot): an overprinted staff-start label (`part_labels.py`, ticket #67). Two different numbers in the gap between two staves of different systems that each sit in both the band above the lower staff and the band under the upper one are read as two numbers, the lower the upper staff's and the higher the lower staff's, but only when the lower is shown to be a bar number and not a stray digit (a volta, a cue's chair, a tempo): it is the upper staff's own label, or counting the staff before it reaches it, or counting the upper staff from it reaches the higher. When that last count reaches the higher number, the bar's reason says the label was overprinted and read as two numbers, counting from the lower; when only the first two checks hold, the later number is kept with confidence 0.05 lower and a reason saying the count did not confirm it. One such number that repeats the label of the staff above and sits nearer to that staff than to the next is that staff's own, printed twice, and is not the next staff's. Staves of one system (joined by barlines) never make a pair or a repeat. Every other number is read as before (a number above a staff labels it). An improvised stretch (chords above the staff and hash marks, with no wording) is not recognised as a solo by itself; a solo needs its marking, as before. A bar count that disagrees with the next staff's printed number is possible (cue notes, repeat signs, unnumbered rests), so check bars against the printed ones; the rehearsal mark and order are the dependable fields. Combined files ("Tenor sax1-2") give solos an ambiguous chair.

Finding a score's parts (`--parts-dir DIR`, or `ParseOptions(parts_dir=...)`; ticket #54, ADR 0004): `DIR` is the planner's parts tree, only read, laid out as `parts/<instrument-folder>/<song file>.pdf` (the folder is the player slot, the filename the instrument). Downloading and organising that tree stays the planner repo's job. Every instrument folder one level down is scanned; `scores/` (the conductor scores) is skipped, as are files that are not PDFs. A file belongs to the score's song when its cleaned title (the filename without noise and its part word) names the score's title, by these rules (code: `songmatch.py`; a part that goes to the wrong song is worse than one reported as matching no song, so they are strict):

- Both titles are reduced to plain words first: case, "the", punctuation, dates ("10-3-26", "10:3:26", "11 3 26", a closing "10 15"), year tags ("JC2026", a year glued to a word), "score", "score1" and the filename noise words listed under `title_noise` in `data/title_aliases.yaml` ("extended", "version", "revised", "expanded", "instr", ...) are dropped. A bracketed group is dropped only when it holds nothing but such words or part labelling ("(lead vocal)"); other brackets are part of the title, so "Medley (Part 1)" and "Medley (Part 2)" are two songs. A title that is only a year or only noise words matches nothing.
- The titles must have the same words. A typo is allowed only word for word and only in long words: the same number of words, each equal or, when both have at least six letters, a close spelling (plain similarity of 85) of the other's. So "Silent Knight" is not "Silent Night" and "Hold Here" is not "Hold Her" (a title that differs from another in one short word is another song). A number is never a typo: digits, roman numerals and spelled-out numbers must be equal, so "Medley 1", "Medley 2" and "Medley II" are three songs, and so are "Christmas" and "Christmas Is", "Do You Hear" and "Do You Hear Me", "I Wish ..." and "We Wish ...".
- A known alias of the title also matches (`data/title_aliases.yaml`: "Merry Super Christmas" is Superstition, "Do You Hear What I Hear" is `do-you-hear`). Spelling variants (Rudolf/Rudolph) and numeral words (Take 5/Take Five) are not guessed: add them there as aliases. These alias groups also feed `--numbers-dir` slug matching (a side effect: the two new groups, `do-you-hear` and `please-come-home`, now match their slugs there too).
- A file title may carry the part's own labelling and nothing else after the song's title (a score's file name may carry some too, "Short Tune pno" also names "Short Tune", and a status word listed under `score_status_words`, "not", ends a score title only). The labelling is a sequence of: instruments (each once, with chair numbers: "Tenor sax 1 2", "TBN 1 2"); the exact phrases listed under `part_descriptions` in `data/title_aliases.yaml` ("lyrics only", "lead sheet", "background singers", "solo", "as solo", "satb", "first", "copy"), word for word and in that order (a long word may carry a typo); a number that follows another word; initials as the last word (two or three letters with no vowel); and as the last word the first three or more letters of a noise word (a file name cut short; never a number). Whatever follows an instrument listed under `free_text_after` (a synthesizer patch name, a note on a vocal part) is labelling. Any other word after the title means another song: "Sing" is not "Sing Sing Sing", "Christmas Is" is not "Christmas Is Coming", "Silent Night" is not "Silent Night Light". A title that itself ends in an instrument word ("... Bass") cannot be told from a score titled without it. Every word of these lists was needed for a real part file to match (checked by removing each in turn); add to them only the same way.
- A file may also start with an instrument ("TRUMPET 1 Short Tune", "Trumpet 1 The Short Tune"; "he" is tried too, a "the" cut short, but "Trumpet 1 He Is Born" still matches "He Is Born"; a lone letter after the title is accepted as a cut-off tag only in such a file); the words after the instrument must then equal the song title. This also strips a real leading instrument word of a title, so a score "Voluntary" takes a file "Trumpet Voluntary" (a trade-off; give such a title distinct words or check the "files matching more than one song" report).

Each matched file is read with part mode (`parse_part`, so every part is in its own report). With the option, `report.parts` is a `PartsReport` (null without it, and nothing else about a normal run changes):

- `parts[]`: the matched `PartReport`s, in folder then file order, each with `file` (`<folder>/<file name>`), `part.player_slot`, `part.instrument`, `part.chairs`, `part.relation` and its `features`. `doublings`, `unexplained` and `unreadable` (matched files whose instrument could not be read) are views of it (library only, not in the JSON).
- `other_files[]`: files of the tree that did not match this song. A file that matches no song at all is one that is in `other_files` of every score of the run.
- `warnings` gets `part <file>: <message>` for each part's own warnings (an unexplained disagreement, an unreadable instrument, a part that could not be read) and, for a song with no parts, "no parts found for this song in the parts directory". A part that fails to read is reported and the other parts are kept. Doublings are not warnings; nothing is corrected.

The lookup is a public function with no side effects: `find_part_files(parts_dir, title)` returns a `PartFiles` (`matched` and `other` paths) from the directory listing and file names alone, no PDF opened and nothing printed; `find_parts(parts_dir, title, options=None)` reads the matched ones with part mode and returns the `PartsReport`. Corpus tests and scripts use these rather than a lookup of their own.

`parse` with `--parts-dir` prints, after the usual summary table, a second table per score (parts found, doublings, unexplained disagreements, unreadable), "files matching more than one song: N" with the files and their scores (the main risk of a title match), and "files matching no song: N" with the file names that matched none of the scores of the run (not counted when a score failed, since its parts are unknown). It stops once up front when `--parts-dir` is not a directory, and refuses an output directory inside the parts tree. An empty tree is fine: every song then warns that it has no parts.

Cross-referencing part solos (`--parts-dir`; ticket #55, ADR 0004): the parts found for a score also feed its `features` and the flow draft. The score stays the structure (sections, order, pages); a part supplies who plays what. Each part's solos are de-duplicated (one per kind, mark and bar; a solo with no bar is dropped when another at that page and mark has one). The score's sections are the bar ranges between its rehearsal-mark printings, each ending at the next printing even when that one prints no bar number (its bar is then estimated between the numbered systems around it); a letter printed twice is two sections, told apart by bar. A part solo belongs to the section its mark and bar point to (a bar up to 4 bars before a mark's first bar still counts, as bar counts drift; a solo with no bar at a reused letter is not guessed). Each part solo is matched to a score feature by rehearsal mark first and bar second, in two passes, parts taken in the instrument order of the score, so named soloists come out in staff order:

1. In its own section, a part solo confirms a feature that names its instrument, names the soloist of an open feature, or is another soloist of a shared feature (one marking over several staves). The nearest by bar among those in the section wins; the closest bar anywhere does not.
2. A solo that found nothing in its own section may match under another mark: within 10 bars for a feature naming its instrument and within 4 bars for an open or shared one (a part may letter a section differently, or count bars a little differently), and never a feature the same part already carries from its own section: that is another solo of the part, and it is added or warned about like any other. When the solo's mark and bar do agree with a section of the score and it still matches a feature of another section, that is a warning ("matched ... across a section boundary: check that it is the same solo"), never silent.

Solo and feature wording do not matter for matching: a part's "solo" matches a score "Clarinet Feature" at the same place (vocal leads are kept apart and never matched).

What the matches do:

- A feature that names the part's instrument gets a reason that the part carries it (when 4 or more parts carry it, one reason with the count), and a missing chair is filled from the part ("Trombone" over a staff of four chairs becomes Trombone 2 when the Trombone 2 part carries it). Another chair that also carries a chairless feature is named too (in `shared_with`), never lost silently.
- An open feature (a "(SOLOS)" over every staff; instrument unknown) gets the parts' instruments and chairs as soloists: the first is `instrument`/`chair`, the rest `shared_with`. A part of several chairs ("Tenor sax1-2") gives an ambiguous chair. Naming a soloist adds 0.3 to the confidence but never lifts it to the flow draft's TODO threshold (0.8), so the draft still asks for a check.
- A named solo has at most 4 players, each chair of an instrument being a player (a section of four chairs at most). A shared feature takes further soloists while it has room, in staff order, and a warning says which part was refused and how many players it already names. 5 or more parts marking one solo (their solos within 4 bars at one mark) is the band's solo, not five soloists: the feature stays open, no one is named, and one reason says how many parts mark it. A band's solo joins an open feature only in its own section: the second printing of a reused letter gets its own open feature.
- A part solo at a mark the score prints, with a bar inside that mark's range and no score feature it matched, is added as a feature found only in parts. The solos left over are clustered first (bars chained within 4 bars at one mark and section, whatever the order of the parts), and each cluster is one feature: on the page of its first bar in the score (so it falls in score order, ADR 0003), with that bar (a bar before the mark's first bar, within the slack, is placed at the mark's first bar, so the order stays page, bar), the confidence at most 0.7 (so the flow draft carries a TODO), a reason saying so, the parts' instruments named, or open when 5 or more parts mark it.
- The flow draft is built after this, so its steps use the named instruments and chairs ("Clarinet and Trumpet 3 solo (A)").

The windows (`NAMED_WINDOW` 10, `NEAR_BARS` and `OPEN_WINDOW` 4 bars), `OPEN_MIN_PARTS` (5), `MAX_NAMED` (4), `MAX_REASONS` (3) and `MAX_PART_SOLOS` (4) are named constants at the top of `crossref.py`. They are tuned on the real scores' bar drift and noise, so change them there, not in the logic.

Real parts are noisy, so a part solo is trusted only where it matches the score. The rest become warnings in the score's `warnings` (`part <file>: ignored N solos (mark A, bar 9, ...): <reason>`), never silent drops: the mark is not a rehearsal mark of the score; the instrument is not in the score's instrumentation (a doubling counts through its player slot); the score marks another instrument's solo within 4 bars; no mark and no score solo near its bar; the part's bar is outside its mark's range in the score; no bar to place it by (a solo with no bar is never added). A vocal part (or the accompaniment in a vocal player slot), and a part with more than 4 distinct solos of its own instrument (a lyrics-heavy part reads as dozens; cues for other instruments do not count), never name a soloist or add a feature: they can only confirm a feature the score already names for them. A "<instrument> solo" cue printed in another part (a "violin solo" in the bass part) adds a reason to that instrument's feature in the score and is never a solo of the part's own instrument. A score feature naming an instrument whose part is present but does not carry it is a warning ("the score marks a Trombone solo (mark B, bar 17) that the Trombone part does not carry"), and the feature is kept; a part that could not be read counts as absent, and so does an instrument with no part in the tree. Without `--parts-dir` nothing changes. The part reports in `parts[]` keep each part's own solos as read; only the score's `features` and `flow` are merged.

Inferring unmarked solos (`--parts-dir`; ticket #66, ADR 0006): a solo is not always marked. The approved corpus facts hold a Clarinet solo at one mark that has no wording anywhere, but from that mark to almost the next the Clarinet is the only wind playing and the others rest in their parts. Each part reports the bars it plays and rests: `parts[].bars` is a list of runs `{first, last, rest}` in reading order, a bar being `rest` when a multi-bar rest covers it and played otherwise (a single bar of silence is not marked in a part, so "played" means "not inside a multi-bar rest"). A bar is told by its number, as in the cross-reference; a bar the count cannot number is left out. With parts, the score's stretches (the bars from one rehearsal-mark printing to the next, at least 4 bars; the last printing has no end and is never read) are checked, and a stretch is a possible solo of one instrument only when all of these hold (code: `infer.py`, constants at its top):

- every wind of the score (woodwind, saxophone, trumpet, trombone, brass; strings are melodic too) and every chair it has is covered by a readable part, a part standing for its own instrument and chairs and its player slot's (a Clarinet part in the alto 1 folder also stands for Alto Sax 1). Otherwise nothing is inferred and a warning says which winds have no part ("unmarked solos not inferred: no readable part for Trombone 4, so who plays is unknown"). A partial parts tree therefore turns the inference off for that song;
- every melodic part's bars cover at least 75% of the stretch (`COVERAGE`). A part with fewer is unknown there, and where that could have hidden a solo a warning says "unmarked solos not inferred at mark B: the bars of some parts could not be read there";
- exactly one melodic part plays (at least half of the stretch), every other melodic part rests at least 75% of it (`REST_SHARE`; a part that half plays blocks the inference) and at least 3 of them rest (`MIN_RESTING`). The rhythm section and the vocals are not counted either way;
- at least 2 of the resting parts play in another stretch (`MIN_ACTIVE`): a lone wind over the rhythm section all song long is the arrangement, not a solo;
- the score has no feature in the stretch, of any kind (a marked solo is never duplicated or overruled; a wind over a vocal lead is a backing).

The result is a `solo` feature of the playing part's instrument (its chair when the part names one), on the page of the mark at the mark's first bar, in score order, with confidence 0.5 (so the flow draft gets a `TODO(score-parser)`) and a reason saying it was inferred from the other parts resting, from which part and bars. It only runs with `--parts-dir`; without it nothing changes.

## Corpus tests

`tests/corpus/` holds opt-in tests against the real local score folder. They are skipped unless `SCORE_CORPUS_DIR` is set, and are never run in CI:

```
SCORE_CORPUS_DIR=/path/to/scores uv run pytest tests/corpus
```

The scores are read in place; nothing is copied or written. The part facts (below) also need `SCORE_PARTS_DIR=/path/to/parts`. One test checks that every PDF in the folder parses. The others compare each score with the approved facts in `tests/corpus/expected.yaml`. Pages and bars match exactly (no tolerance), so a bar one off fails.

To add facts, first get the user's approval for each one, then add an entry keyed by the PDF file name without `.pdf`:

```yaml
scores:
  some-score-file-stem:
    instruments: [Alto Sax, {name: Trumpet, chairs: [1, 2, 3, 4]}, {name: Wood Block, xfail: "why the tool misses it"}]
    max_features: 13                  # at most this many features in the report
    features:
      - {instrument: Alto Sax, page: 5, bar: 29}
      - {instrument: Guitar, chair: 2, page: 24, bar: 143}
      - {instruments: [Clarinet, Trumpet], kind: shared, page: 1, bar: 9, mark: A}
      - {instrument: Vocal, kind: vocal, voice: female, page: 3, mark: B}
    not_features:                     # false positives that must not appear
      - {instrument: Baritone Sax, page: 5}
    order:                            # features in score order, not necessarily adjacent
      - {instrument: Piano, page: 1}
      - {instrument: Tuba, section: B}
    parts:                            # part files of the song (needs SCORE_PARTS_DIR)
      - {slot: flute, instrument: Piccolo, relation: doubling, solos: [{page: 2, mark: C, bar: 17}, {page: 5, mark: E}]}
      - {slot: trumpet-3, instrument: Trumpet, chairs: [3], max_solos: 0}
      - {slot: bass, instrument: Electric Bass, xfail: "why the part is not met yet"}
```

- Instrument keys: `name`, `chairs` (the instrument's chairs must equal this list exactly) and `xfail`.
- Feature keys, all optional except the instrument: `page`, `bar` and `mark` (rehearsal mark) match exactly; `chair` (the feature must carry that chair); `kind` is `instrument`, `vocal` (instrument `Vocal`, matched to features of kind `vocal lead`) or `shared`; `voice` (`female` or `male`, for vocal leads); `open: true` replaces the instrument and stands for an open solo, a feature with no instrument (use it with `page`, `bar` and `mark`); `instruments` lists several instruments that must each have a feature (or be named by a shared feature) at the same page, bar and mark (use it with `kind: shared`).
- `section` is another name for `mark` (the rehearsal mark the flow draft groups by), usable in feature, `not_features` and `order` entries.
- `order` lists feature entries, each naming one `instrument` plus the usual `page`, `bar`, `mark` or `section`, `chair`, `kind`, `voice` keys, that must appear in that order in the report, not necessarily next to each other. A feature shared by several instruments matches an entry for any of them. An entry takes no `instruments`, `open`, `kind: shared` or `xfail` (a malformed entry is reported, not ignored). A fact giving both `mark` and `section` must give the same value. Each entry must match a feature after the one matched before it. Because `report.features` is in score order, this asserts "Tuba p8 follows Piano p1" without exact bars.
- `xfail: reason` records a fact the tool does not meet yet. It must keep failing: once it passes, the test fails and asks you to remove the `xfail`.
- `not_features` lists instrument features that must not be found (given `page`, `bar` or `mark` to narrow them down).

- `parts` lists the song's part files (ADR 0004): who plays what, which the score cannot say. The parts are read in place from `SCORE_PARTS_DIR`, the `parts/<instrument folder>/<song file>.pdf` tree (opt-in like `SCORE_CORPUS_DIR`: the part tests skip without it and never run in CI). A song's parts are found with the library lookup `find_parts` (the one behind `--parts-dir`, described above), given the cleaned score file name as the title. A part gives `slot` (the instrument folder it sits in: the player slot) and `instrument` (the filename's part word, so a Piccolo part in `flute/` is `{slot: flute, instrument: Piccolo}`), and optionally `chairs` (the part's chairs equal this list exactly), `relation` (`same`, `doubling`, `unexplained` or `unknown`, as `part.relation`), `max_solos` and `solos`. `max_solos` counts every feature the part reports (vocal leads and every other kind included), and a solo fact matches a feature of any kind. A solo gives `page` and, when known, `mark` and `bar`, matched exactly; the listed solos must appear in that order in the part, not necessarily next to each other. A part and a solo each take `xfail: reason` (a solo with an xfail leaves the order check). A part fact that names no such part is a mismatch, and a malformed part fact (no slot or instrument, an unknown key, a solo with no page, an empty xfail) is reported, not ignored. Two facts for the same slot, instrument and chairs are reported as one part stated twice, and a solo's stale `xfail` is reported even inside an `xfail` part.

Facts stay short and hold no music content: instrument names, page, bar and marker only (for a part, its player slot, instrument and chairs; never a file name).

`scripts/corpus_counts.py [DIR]` (default `$SCORE_CORPUS_DIR`) prints per-score counts to stdout: instruments, features, features with no bar, features with no instrument, features with no rehearsal mark, features whose mark is carried from an earlier page and warnings, so two runs can be compared. With `--parts-dir DIR` (default `$SCORE_PARTS_DIR`) it adds two columns: the parts found for each score (by song title, as above) and the solos read in them. Rows are numbered by sorted position; `--names` adds the file names. It prints numbers only and writes nothing.
